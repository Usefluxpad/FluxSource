# PostgreSQL provider package (`prisma/postgres/`)

Production PostgreSQL configuration for FluxPad, kept **fully separate** from
the SQLite development setup under `prisma/`. Nothing in the SQLite tree was
modified; no database was created, reset, or migrated by this phase.

## Contents

| File | Purpose |
|---|---|
| `schema.prisma` | Provider-ready schema: `provider = "postgresql"`, `url = env("POSTGRES_DATABASE_URL")`, generator output `./generated-client`. Model definitions are **byte-identical** to `prisma/schema.prisma` (this file is generated from it, so they cannot drift by hand-edits). |
| `migrations/00000000000000_init/migration.sql` | PostgreSQL-native baseline DDL **generated by Prisma 6.16.2's own PostgreSQL connector** (`prisma migrate diff --from-empty --to-schema-datamodel prisma/postgres/schema.prisma --script`). It is NOT a reinterpretation of the SQLite migration SQL. Regenerating the diff reproduces this file byte-for-byte (verified). |
| `migrations/migration_lock.toml` | `provider = "postgresql"` — marks this migration history as PostgreSQL-only. |
| `generated-client/` | Proof-of-generation client build (created by this phase's verification; a build artifact, safe to delete/regenerate). |

## Connection requirements

- PostgreSQL **14+** (Prisma 6.16.2 supported versions; JSONB, `TIMESTAMP(3)`,
  native enums used).
- Connection string in `POSTGRES_DATABASE_URL`, e.g.
  `postgresql://USER:PASSWORD@HOST:5432/DATABASE?schema=public`.
  Never commit real credentials; the variable is read by the server process
  only. Development SQLite keeps using `DATABASE_URL` — the two never collide.

## Migration commands (production, empty database)

```bash
# 1. validate the schema
npx prisma validate --schema prisma/postgres/schema.prisma

# 2. apply the committed PostgreSQL baseline to the empty production database
npx prisma migrate deploy --schema prisma/postgres/schema.prisma

# 3. generate the PostgreSQL client into the isolated output
npx prisma generate --schema prisma/postgres/schema.prisma
```

`migrate deploy` applies `migrations/00000000000000_init/migration.sql` and
records it in `_prisma_migrations`. It never resets data. Schema evolution
after launch: create further migrations with
`prisma migrate dev --schema prisma/postgres/schema.prisma` against a staging
database, then `migrate deploy` in production.

## Deployment steps (application side)

1. Provision the empty PostgreSQL database; set `POSTGRES_DATABASE_URL`
   (server-side only).
2. Run the three commands above.
3. Switch the **runtime** client to PostgreSQL: either (a) flip
   `prisma/schema.prisma`'s `provider` to `"postgresql"`, point `DATABASE_URL`
   at the same database, and `npx prisma generate` (the path documented since
   the first schema), or (b) import the client from
   `prisma/postgres/generated-client` via a small alias in `src/lib/db.ts`
   (option (a) is the current documented path; (b) avoids touching the main
   schema and is a one-line import change).
4. Restart the app; the first summary read creates rows via the same code paths.

## Rollback considerations

- `migrate deploy` on an empty database: rollback = drop the database/schema;
  nothing else exists to unwind.
- After real data exists: Prisma keeps `_prisma_migrations` history; roll back
  by applying a new down-migration — Prisma does not auto-generate down SQL,
  so any destructive change should be reviewed as its own migration.
- The application can keep running on SQLite at any time; the providers are
  independent trees and the client outputs are isolated.

## Unverified assumptions

1. Prisma 6.16.2 PostgreSQL DDL is valid on the target PostgreSQL server
   version (generated DDL uses only standard features; verify with the
   commands above on staging first).
2. `prisma migrate deploy` ordering/locking behavior in the target hosting
   (single deployer recommended).
3. Production connection pooling (PgBouncer/serverless poolers) — if used,
   enable Prisma's pgbouncer-friendly settings; not configured here.
